**The ingestion API** (RecipeParser, its own repository under `Projects\RecipeParser`, recorded here because the client is where the damage shows)

- A chunk whose extraction reply comes back as truncated JSON is dropped in silence. The extractor catches the parse error, logs it, returns nothing, and the pipeline treats the chunk as empty: no retry, no count, and a job that finishes this way still reports success. Observed 2026-09-04 during a live import of an 827-recipe Paprika export, twenty recipes lost in the first hour, roughly one in forty, with no way to learn which. The same entries extract cleanly when retried, singly and four at a time, so the reply is occasionally bad rather than the recipe being unparseable. The fix has three parts: retry a parse failure before giving up; carry a skipped count through to the job row so the client can say "812 of 827 imported"; and log the reply's finish reason and first line, which is what distinguishes truncation from malformed content. ([#6](https://github.com/IanDBallard/RecipeParser/issues/6))
- Nothing is written until every chunk is done. The pipeline processes the whole file and the API writes the results in one call afterwards, so a large import shows an in-progress job for hours with an empty library behind it, and a restart in that window loses the entire run. Incremental writes, per recipe or per batch, would also give the client real progress instead of a spinner. ([#7](https://github.com/IanDBallard/RecipeParser/issues/7))
- The job row's `progress_pct` is only ever 0 or 100. Every stage update writes the stage but never the fraction, so the client's progress bar cannot move even though the parser knows how many chunks it has finished. ([#8](https://github.com/IanDBallard/RecipeParser/issues/8))
- Photographs are read and then dropped. The Paprika reader pulls each entry's embedded photo out of the archive and attaches the bytes to the chunk; nothing downstream ever reads that field, and the recipe row is written with whatever image address the recipe already carried, which for a Paprika entry is none. The one upload helper in the API takes a web address, downloads it and stores the result, cannot accept bytes, and is called from nowhere. Measured on the 2026-09-04 import: 466 of 827 entries carried a photo and none arrived. The storage bucket exists, is public and already holds images the retired mobile client uploaded, so only this path is missing. ([#9](https://github.com/IanDBallard/RecipeParser/issues/9))
- Reading a job's status and pausing, resuming or cancelling it are unauthenticated. The three ingestion endpoints verify the bearer token; these four take a job id and nothing else, so anyone who can reach the API can cancel someone else's import. Confirmed by an unauthenticated request returning 404 for a missing job rather than 401. ([#10](https://github.com/IanDBallard/RecipeParser/issues/10))
- The service key is read under two different variable names in different modules, `SUPABASE_SERVICE_KEY` and `SUPABASE_SERVICE_ROLE_KEY`. Both happen to be set locally; setting only one would disable a subset of writes with a warning rather than an error. ([#11](https://github.com/IanDBallard/RecipeParser/issues/11))
- An ingredient the source never quantified is stored with an amount of zero, because the extraction schema has no way to say "no quantity". Clients cannot tell that from a real zero. The web client now drops a zero rather than printing "0 Kosher salt", but the representation is the underlying problem. ([#12](https://github.com/IanDBallard/RecipeParser/issues/12))
